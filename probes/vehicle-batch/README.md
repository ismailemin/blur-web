# vehicle-batch — the vehicle staging compiler

One spec list plus one command replaces the hand chain for every remaining car:
stage the model, build the part manifest/mesh/scene report, traverse materials,
decode the wheel model, and emit the roster / ghost / guard-pin fragments.

It is a **staging** compiler. It never edits `probes/e1-drive`,
`probes/car-parts`, `probes/car-materials`, `tools/`, the web application, the
engine, `upstream/` or `game-data/`, and it makes no drive claim.

## Inputs

| input | authority |
| --- | --- |
| `spec/cars.json` | generated by `tools/spec_gen.py` from `_work/vehicle-pipeline/cars.json`, `c-aliases.json`, `amax-vehicles.jsonl` and the proven HUD parsers |
| decoded body models | `_work/vehicle-pipeline/models/`, re-decoded from `root.pak` by `build_all_manifests.extract` (committed mapper/decoder) |
| part manifest/mesh/scene | `probes/car-parts/tools/build_manifest.py` (called through `build_all_manifests.build_manifest`) |
| materials | `tools/inspect_car_materials.py` (called through `stage_batch3.material_pass`) |
| wheel model | `root.pak` via `stage_batch3.decode_wheel`; read by the committed `scene_inspect.exe` / `model_inspect.exe` |
| HUD name/icon | `hud_catalog.py` parsers over `vehicles.loc`, `amax.bin`, `car_icons*.ipf` |

No decoding, offset or colour logic is reimplemented here; the compiler only
orchestrates the proven builders and pins their bytes.

## Commands

```powershell
$py = "C:/Users/ismailemin/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe"

# regenerate / check the 62-car spec
& $py probes/vehicle-batch/tools/spec_gen.py
& $py probes/vehicle-batch/tools/spec_gen.py --check

# plan only
& $py probes/vehicle-batch/build.py --dry-run

# stage every record not in the 57-car roster (default scope)
& $py probes/vehicle-batch/build.py

# one car / several cars, by slug or record index
& $py probes/vehicle-batch/build.py --only bmw-m3e92-drift
& $py probes/vehicle-batch/build.py --only 59,60,73

# force a rebuild (resume is on by default)
& $py probes/vehicle-batch/build.py --no-resume

# second independent build + gate
& $py probes/vehicle-batch/build.py --out-root _work/vehicle-batch/_repeat --no-resume
& $py probes/vehicle-batch/verify.py

# batch-roster gate: fields/model/artifact re-derivation, order, determinism
& $py probes/vehicle-batch/tools/verify_batch_roster.py
```

Exit codes: `0` when every selected car is staged or blocked with a typed
reason; `1` when a car is `partial` or an unexpected `error` occurred.

`batch-roster.json` is complete only for a full `--scope remaining` run (the
default). A `--only` run writes the selected subset and the roster gate will
report the missing entries.

## Spec schema (v1)

`spec/cars.json` is `{kind:"blur.vehicle-batch.spec", version:1, sources, counts,
cars[]}` with 62 entries, one per `RP_CarDynamics` record. Each entry carries:

| field | meaning |
| --- | --- |
| `slug`, `recordIndex`, `recordId`, `recordName` | identity (from the audit) |
| `class` (`A`/`B`/`C`), `classReason` | V1 classification |
| `scope` (`roster`/`remaining`), `rosterPosition` | whether it is already in the 57-car roster |
| `drivetrain`, `massKg`, `gears` | roster `layout` inputs |
| `physics.fieldsPath/fieldsSha256/gatePass/driveType/wheelBase` | `car_xt` field list and gate |
| `body` | `route` (`exact`/`alias`), `pakPath`, `logicalBytes`, `sha256`, `decodedPath`, `rule`, candidates |
| `bodyReason` | typed `{code, detail}` when there is no body (only `DefaultCar`) |
| `alias` | the record-level `AmaxVehicle.dynamics` evidence for a class-C body |
| `wheel` | `pakPath`, `logicalBytes`, `sha256`, `decodedPath`, `source`, `proof{status,provenDraws,previewDraws,tyreProofTier,caliper}` |
| `hud` | `nameKey`, `name`, `fullNameKey`, `fullName`, `hudNameKey`, `hudName`, `iconSprite`, `iconTag`, `iconSpriteKnown`, `iconPages`, manufacturer |
| `blockers[]` | `{kind, detail, source}` typed statements already known before staging |
| `evidence` | `inCommittedRoster`, `batch3Staged`, `v1Mapped` |

Unknown or absent values are `null` next to a typed reason (`wheel.reason`,
`hud == null`, `bodyReason`); a spec field is never invented. In
`batch-roster.json` a blocked staging record becomes `status:"unsupported"` with
the typed reason and the exact `missing` field/byte.

## Output layout

```
_work/vehicle-batch/
  summary.json             machine-readable run report (counts, aggregates, records)
  batch-roster.json        staged/unsupported roster for the remaining records
  batch-roster-verify.json gate output (probes/vehicle-batch/tools/verify_batch_roster.py)
  roster.fragment.json     entries to append to probes/e1-drive/cars/roster.json
  ghost.fragment.json      pending ghost index entries (2 courses × staged car)
  guard-pins.json          per-car pin values for the four integration guards
  verify.json              gate output (probes/vehicle-batch/verify.py)
  cache/models/            decoded bodies (content-addressed by SHA-256)
  cache/wheels/            decoded wheel models
  _repeat/                 second independent build (determinism baseline)
  _regression/             one roster car rebuilt for path-independence proof
  <slug>/
    manifest.json          car-part manifest (committed builder)
    mesh.json              LOD0 positions/indices/UV0
    scene-report.json      committed Scene reader output (filtered when a
                           skip-empty-draws decision applies)
    scene-filtered.json    filtered scene fed to the builder (skip-empty-draws only)
    scene-report.raw.json  raw Scene reader output (skip-empty-draws only)
    materials/             independent material traversal (3 files)
    wheels/wheel.json      wheel model identity/hashes + scene/model summary
    wheels/scene.json      full wheel scene_inspect output
    wheels/model.json      full wheel model_inspect output
    ghost-inputs.json      the two ghost files this car needs, inputs, command
    integration.json       roster entry, ghost index fragment, guard pins, patch order
    staged.json            resumable identity: input hashes + artifact hashes + record
    blocked.json           typed reasons only (blocked cars; no manifest)
```

`staged.json` is the resume key: a car is skipped only when its spec entry, body
hash, wheel path and the builder hashes match and every artifact hash still
matches. `staged.json` carries `schema:2`; a schema change forces a rebuild.
Nothing is written under another probe's tree.

## Batch roster (remaining 5)

`build.py` writes `_work/vehicle-batch/batch-roster.json` with one entry per
selected record, in record-index order. The committed roster now holds 57 cars,
so the remaining scope is the five records that the part builder or the audit
still refuses. An entry carries:

| field | meaning |
| --- | --- |
| `slug`, `recordIndex`, `recordId`, `recordName` | identity |
| `class`, `scope`, `drivetrain`, `massKg`, `gears`, `wheelBase` | roster inputs |
| `fields` | `path`, `bytes`, `sha256`, `fieldCount` re-derived from the committed `.fields` file |
| `model` | `route` (`exact`/`alias`), `pakPath`, `sha256`, `decodedPath`; `null` only for `DefaultCar` |
| `artifacts` | staged `manifest`/`mesh`/`sceneReport` bytes + SHA-256; `null` when unsupported |
| `builderDecision` | the typed decision that let the committed builder stage this car (`null` otherwise) |
| `status` | `staged` or `unsupported` |
| `unsupported` | `code`, `detail`, `summary`, `source`, `missing`, `diagnosis` and the full `reasons[]`; `null` when staged |

`status:"staged"` means the committed `.fields` bytes/hash/count, the decoded
body model, the part manifest, the LOD0 mesh and the scene report were
re-derived and agree. `status:"unsupported"` means the committed chain refused
the record; `missing` names the exact field/byte (for example `body.model`,
`wheel.caliper.parent`, `wheel.elementCount`). No value is invented and no model
mapping is fabricated.

### Builder decisions (2 staged)

Two refusals are resolved by a typed decision that uses only committed data.
The decision is recorded in `spec/cars.json` (`builderDecision`) and in each
`staged.json` record; `probes/vehicle-pipeline/tools/stage_batch3.py` applies it
to the committed builder. **The main agent must port the same decision into
`probes/car-parts/tools/build_manifest.py`** before the committed build can
reproduce these two manifests.

| # | slug | decision | evidence |
|--:|---|---|---|
| 38 | `ratrod-na-stock` | `wheel-axis-from-parent-envelope` | The rear brake-disc element local bounds are offset along X (`E_BrakeDisc_BackLeft` X `1.429031..1.498138`) while its matrix translation equals the `e_wheel_backleft` parent, so the member union is `[1.626399, 0.846300, 0.846300]`. The parent's own serialized bounds `[0.272146, 0.876655, 0.833748]` are thin on X and round on Y/Z (relative delta `0.0489`); the front wheels already pass on their member union. The axis is therefore X; no axis is invented. |
| 79 | `toyota-supra-smooth` | `skip-empty-draws` | Scene draws 48 and 50 have `indexCount: 0` at `firstIndex` 57156 and 57192. They contribute no geometry; the other 82 draws are classified unchanged. The raw reader output is kept as `scene-report.raw.json` and the filtered scene is fed to the committed builder through `--scene-json`. |

### Unsupported (3) — exact reason per car

| # | slug | missing | exact builder/audit statement |
|--:|---|---|---|
| 8 | `defaultcar` | `body.model` | no vehicle record and no body model reference; `DefaultCar` is a physics fallback, not a car body |
| 58 | `hummer-h2-rat` | `wheel.caliper.parent` | `E_BrakeDisc_FrontRight1` (element 26) and `E_BrakeCaliper_FrontRight1` (element 27) are parented to `DefaultElement` (0); the chains are `[26 -> 0]` and `[27 -> 0]`, not a wheel. The front-left wheel has only `e_tyre_frontLeft` + `e_alloyRim_frontLeft`; re-parenting the orphans would invent a parent chain. |
| 67 | `ford-supervan-stock` | `wheel.elementCount` | 14 recognized wheel elements because the two rear calipers are named `E_Brake_Caliper_BackLeft/BackRight` (not `E_BrakeCaliper_*`); both are direct children of `e_wheel_backleft/backright` and their element bounds are model-space (matrix translation 0). Recognizing the name gives 4 members per corner, but only 2 caliper draws exist (frontleft/frontright, draws 24/25); the builder's caliper assignment requires 4. |

These three are committed-builder/audit refusals, not compiler bugs. Nothing is
guessed, borrowed or substituted. The 2 staged cars are data only — no car is
claimed playable.

## Integration contract

The compiler produces data and pins; the main agent performs the integration in
this order (also embedded per car in `integration.json.patchOrder`):

1. append `roster.fragment.json.entries` to `probes/e1-drive/cars/roster.json`;
2. `python probes/e1-drive/tools/car_roster.py`;
3. `python probes/car-parts/tools/build_all_manifests.py` — `mesh.json` and
   `scene-report.json` must be byte-identical to this compiler's artifacts (the
   `_regression` check proves the build is path-independent; the manifest differs
   only in `source.model`);
4. `python probes/car-materials/tools/build_roster_materials.py` and
   `verify_roster_materials.py` with the roster-length guard;
5. `python probes/e1-drive/tools/build_car_textures.py` (re-pin
   `COMMITTED_ROSTER_INDEX`, `COMMITTED_CAR_INDEX`, `COMMITTED_SCENE_REPORTS`);
6. `node probes/e1-drive/tools/build_geometry.mjs` (re-pin
   `COMMITTED_MANIFESTS`, `COMMITTED_CAR_INDEX`, `COMMITTED_CAR_TEXTURES`,
   `COMMITTED_CAR_COVERAGE`);
7. `node probes/e1-drive/tools/verify_e1_drive.mjs --write-ghosts`;
8. `node probes/e1-drive/tools/verify_e1_drive.mjs` and
   `python tools/verify_asset_probe.py --skip-build`;
9. `node probes/e1-drive/tools/capture_browser.mjs --mode sprint` per added car.

Authoritative pin values:

- `mesh` / `scene-report` hashes from `guard-pins.json` are final (proved equal
  to the committed build);
- the committed `manifest` hash must be read from the regenerated
  `_work/car-parts/cars/index.json` (the staged manifest records the staging
  cache path in `source.model`);
- P52 texture counts/RGBA and ghost values come from the steps above, never from
  this compiler.

## Verification

`verify.py` checks the spec (62 records, unique ids, typed reasons), every staged
car (artifact presence, hashes, cross-document draw counts, wheel and ghost
inputs), determinism between two build roots, duplicates, aggregates, and one
path-independence regression.

`tools/inspect_builder_decisions.py` re-derives the five remaining refusals
(wheel parents/members, orphan parent chains, empty draws) from the decoded
models and the committed Scene reader; it writes
`_work/vehicle-batch/builder-decisions.json` and edits nothing.

`tools/verify_batch_roster.py` is the roster gate. It re-derives every entry from
the committed source (`.fields` bytes/hash/count, decoded body model, record
identity, drivetrain, mass, wheelbase), checks the staged manifest/mesh/scene
hashes and their internal arithmetic, checks the typed unsupported reason and
`missing` field, checks record-index order and uniqueness, proves the batch
roster plus the committed 57-car roster covers all 62 records exactly, and
compares the primary and repeat build roots byte-for-byte. It prints
`N/M checks passed` and exits `1` on failure.

```powershell
& $py probes/vehicle-batch/tools/verify_batch_roster.py
# batch roster: 2 staged, 3 unsupported, coverage 59/62
# PASS 261/261 checks passed
```
